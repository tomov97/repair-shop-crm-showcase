# Data Model

## Overview

The v1 data model is customer-first rather than machine-first.

This is intentional:
- customers may return many times
- machine descriptions can vary across visits
- a customer may bring different machines over time

v1 should preserve customer history without pretending that machine identity can always be matched reliably across visits.

## Core Entities

## Customer

Represents the person bringing machines to the shop.

Suggested fields:
- `id`
- `full_name`
- `normalized_phone`
- `display_phone`
- `created_at`
- `updated_at`

Rules:
- a customer can have many intakes
- normalized phone is used for matching and search
- display phone preserves the originally entered presentation

## Intake

Represents one machine received by the shop.

Suggested fields:
- `id`
- `customer_id`
- `intake_number`
- `scan_token`
- `brand`
- `model`
- `issue_description`
- `notes`
- `is_archived`
- `charged_amount`
- `coffee_count`
- `created_at`
- `updated_at`
- `archived_at`

Rules:
- one intake equals one machine
- `intake_number` is unique and generated by the system
- `scan_token` is unique and used for QR retrieval
- `charged_amount` is required when archiving
- `is_archived` replaces stage logic in v1

## Print Job

Represents one attemptable label print action.

Suggested fields:
- `id`
- `intake_id`
- `label_asset_url`
- `status`
- `attempt_count`
- `last_error`
- `created_at`
- `updated_at`
- `printed_at`

Suggested status values:
- `queued`
- `printing`
- `printed`
- `failed`

Rules:
- print jobs must be retryable
- a reprint creates a new print job
- job records must survive temporary printer or PC failure

## Audit Event

Tracks important changes quietly without creating a heavy workflow system.

Suggested fields:
- `id`
- `entity_type`
- `entity_id`
- `event_type`
- `actor_id`
- `payload`
- `created_at`

Suggested tracked changes:
- intake created
- customer linked manually
- key field edited
- archived
- reprint requested
- print failed

## Matching Rules

### Auto-Link

Auto-link a new intake to an existing customer only when:
- normalized phone matches
- name matches

### Manual Confirmation

Require manual confirmation when:
- phone matches but name differs
- name matches but phone differs

This prevents silent bad merges while still keeping repeat-customer history useful.

## Search Rules

Search should support:
- normalized phone matching
- customer name matching
- intake number matching

Search results must include current and archived intakes, with current intakes ranked first.

## Editing Rules

- Basic edits are allowed in v1.
- No hard delete for customers or intakes.
- Key edits should create audit events.

## Archive Rules

Archiving means the intake is no longer current.

Required on archive:
- charged amount

Not required in v1:
- pickup date
- repair summary
- completion stage

## Privacy Rules

- QR routes use `scan_token`, not raw customer data.
- Customer personal data must stay behind authentication.
